# Directional counters from anonymous acknowledgements and blind receipts

**The raw two-operation experiment is implemented and tested; no participation policy is selected.** The [directional receipt composition](../experiments/directional-receipts/README.md) counts a named account's authorized acknowledgements and later counts blind receipts redeemed by another authenticated account. All 22 tests pass at cfrm `207a8df6e767bda9523da531682425d4b879470c`, including honest reversed actions, transactional recovery and explicit pooled-credit attacks. It does not establish truthful delivery, nontransferable prover identity, the simulator's complete pair semantics or a production controller.

A separate [first-contact release proposal](https://github.com/corbet-labs/cmsg/blob/main/studies/first-contact-release-gate.md) could require a receive debit before an honest sender releases first content. The current raw ledger has no release nonce or signed release attestations. Its voluntary-redemption limitation must not be mistaken for a final policy choice; [the next bounded specification](../experiments/directional-receipts/ATTESTATION-ACCEPTANCE.md) separates that conditional release mechanism from truthful delivery claims.

The decisive distinction is between **direct self-credit**, which the existing sender-excluded Semaphore group prevents, and **credit reassignment by another qualified participant**, which it does not. Rejecting the second would require a relationship between hidden values that the current constructions do not prove. Accepted bounded collusion can make this a policy tradeoff, but its concentration bound is larger than one credit per colluding friend.

## What the existing constructions establish

The [registered acknowledgement code](../experiments/private-reciprocity/acknowledgement.js) verifies a qualified anonymous member other than named sender `S`, with one lifetime nullifier per prover and `S`. The existing [Semaphore circuit](https://github.com/semaphore-protocol/semaphore/blob/v4.13.0/packages/circuits/src/semaphore.circom) constrains membership, a scope/secret nullifier and an arbitrary public message. It does not interpret that message as a delivery assertion or inspect an RSA-blinded payload. Binding a request hash into the message prevents substitution; it does not prove what the hidden request contains.

The [permit experiment](../experiments/anonymous-permits/permits.js) already uses RFC 9474 randomized blind RSA. Blindness separates the signed message from the issuance transcript, while one-more unforgeability bounds distinct valid messages by signing interactions, under the stated assumptions. The RFC explicitly leaves proofs of hidden message structure outside its scope. A signature therefore cannot establish that a hidden recipient field identifies the Semaphore prover. [RFC 9474 §§4, 7 and 7.2](https://www.rfc-editor.org/rfc/rfc9474.html#section-7.2)

The earlier 105 passing tests at cfrm `11acb6a30c23b28abaafe4c10e228efdaed90aae` cover the separate rule, rendezvous, permit, acknowledgement, enrollment and checkpoint experiments. The new [22-case suite](../experiments/directional-receipts/receipts.test.js) additionally composes actual Semaphore proofs, immutable authenticated enrollment, cvld admission signatures and RFC 9474 blind RSA. A complete numerical policy controller remains unimplemented; the endorsement-only alternative in the [observables study](private-accounting-contract.md) remains unselected.

## Candidate flow and exact counter meanings

Let `S` be the named authorizer and `R` the anonymous acknowledging member. Both have current cvld qualification and immutable enrolled identities. All clients validate the same complete qualified checkpoint, excluding precisely `S`, with the existing anonymity floor.

1. **Recipient prepares its own receipt request.** `R` creates fresh blind-RSA client state and a fixed-format receipt containing a random serial, a common community/type/epoch context and its own stable account ID. The account ID is hidden during issuance. The honest client never uses a blind request supplied by `S`. A complete client must persist the unblinding state encrypted before asking for issuance; the current composition fixture retains it in memory and does not implement that recovery adapter.
2. **Sender expressly authorizes one debit.** `S` signs a fresh random authorization with its certified chat key. The signed canonical context covers purpose, community, policy, named `S`, expiry, nonce and the hash of `R`'s blinded request. There is no recipient ID. Binding the request requires a preparatory peer exchange; omitting it makes the authorization itself transferable to a different receipt request. The signature means “authorize one acknowledged-send counter update,” not “I prove text was delivered.” A copied certificate is insufficient.
3. **Recipient acknowledges anonymously.** `R` proves membership in the sender-excluded set. The public proof message commits to the checkpoint, complete signed authorization and blinded-request hash. The lifetime scope remains derived from community and `S`, without epoch, nonce, conversation, group or action-role suffixes. The isolated experiment supplies this explicit message contract while reusing the current maintained circuit unchanged.
4. **One transaction records the sender side.** After checking the current grant, signature, proof, limits and expiry, cfrm consumes the authorization nonce and lifetime nullifier, increments `S.authorizedSend`, and commits exactly one blind-signature response for that exact request. The response is returned only after commit. This counter means one authorized debit acknowledged by a distinct qualified identity. It does not mean a text message was sent or read. A retry returns the same response and increments nothing.
5. **Recipient voluntarily records its side later.** `R` unblinds and redeems the receipt with current admission and purpose-bound certified-key possession covering that receipt, its context and a fresh challenge. An unrelated authenticated session is not permission to debit the account. The signed hidden account field must equal that authenticated account. One transaction consumes the receipt serial and increments `R.acknowledgedReceive`. No sender ID, authorization nonce, proof nullifier, blinded-request hash, conversation ID or group ID appears in redemption. The counter means redemption of one receipt arising from a distinct accepted authorization somewhere in the cohort; it does not prove that the redeemer was its acknowledging prover.

The sender learns its recipient through the private conversation, as before; the proposed operator payloads contain only one named side at each phase. This removes an explicit pair field. It does not by itself remove correlation from timing, client identifiers or small cohorts.

An honest `R` can later authorize a reversed action, with `R` named and `S` anonymously acknowledging. Its receipt is redeemed by `S`. The four resulting counter increments match the simulator's accepted introduction and first reply, conditional on both parties following this protocol. Only the introduction uses the existing first-contact allowance. Ordinary conversation replies remain free. A trusted recipient client still uses encrypted local contact history to distinguish a reply from a new introduction.

An unanswered or declined introduction produces no such acknowledgement counter, whereas the simulator increments its sender on delivery. Its independent permit issuance still costs an allowance unit. These two observations must remain separate; this candidate does not silently recover the simulator's delivery counter.

## Attacks, limits and conditional guarantees

| Attack or failure | Candidate result and remaining limit |
|---|---|
| Outsider sends unsolicited traffic or an endorsement targeting `S` | No sender counter or maturity change without `S`'s current, purpose-bound debit authorization. An old unexpired authorization can be exercised once, so its validity must be bounded; silence does not revoke already signed permission. |
| Outsider submits a receipt “for” an unwilling target | No receive counter change without that target's authenticated redemption. Possession of its public certificate or ID is insufficient. |
| `S` acknowledges itself | Sender exclusion plus immutable enrollment rejects its own Semaphore identity. Another qualified identity is necessary. This establishes distinct admitted identities, not distinct humans. |
| Someone replaces an honest recipient's blinded request | The sender authorization and proof both bind the exact request. An honest recipient checks that it is the request it prepared; substitution is rejected. |
| Receipt is transferred after honest preparation | Its signed recipient field requires redemption by that same authenticated ID. Sharing the token alone cannot reassign it. A pure bearer variant lacks this protection. |
| Malicious `R` prepares a receipt naming `S` or `Q` from the outset | It can produce a valid anonymous proof for that request. The issuer cannot check the hidden account field against the prover. Redemption then credits the designated account. This survives the honest-preparation mitigation and requires no forgery. |
| `R` acknowledges but abandons the receipt | `S`'s committed debit remains; no recipient debit appears. Idempotent recovery helps interruption, but voluntary abandonment cannot be distinguished from loss. No refund follows a claimed failure. |
| Receiver reads already supplied messages and suppresses receipt redemption | The raw two-operation boundary permits omitted bookkeeping. A recipient-only UI check cannot prevent it. The separate sender-side release proposal may require the debit before honest first-content release, but still cannot prove reading or enforce dishonest senders. |
| Same authorization is presented by many different members | One nonce permits one transaction, even if all proofs have different nullifiers. The winning request is fixed; the others cannot mint receipts or consume their pair nullifier in a failed transaction. |
| Same prover uses fresh authorizations, epochs, groups or chat keys with `S` | The lifetime nullifier permits only one accepted event. Updating checkpoints and ordinary chat-key rotation do not reset it. |
| First action reverses its named and anonymous roles | This creates a different directed nullifier. It can represent the honest first reply, but cannot prove that an earlier event involved the same pair. Global unordered-pair uniqueness and “this is the reply to that introduction” remain unproven. |
| A group invitation claims one action covers 99 new members | One authorization and receipt cannot authorize 99 independent first-contact acceptances. Each compliant recipient needs its own first-contact gate. Group joining does not imply reciprocal interactions with every other group member. |

The current anonymous permit redemption contains no account IDs. The current acknowledgement contains no spent-permit proof. Running the calls in sequence does not prove they refer to one introduction. Preserve their separate meanings: existing permits bound compliant recipient gates globally; the proposed named-sender transaction can separately cap acknowledged authorizations under `S` despite permit pooling. It cannot bound raw unsolicited packets or certify a debit on first delivery. No connection between these two ledgers is implemented by this study.

### Quantifying the accepted collusion

Assume immutable enrollment, one lifetime scope per named account, one receipt per accepted directed event, no key compromise or new identities, and `M` fixed qualified identities. For a closed colluding subset of size `k`:

- Each member, as the **named sender**, can obtain at most `k−1` acknowledgements from the other colluders. Thus returning receipts from its own authorizations can balance at most `k−1` of its own send debits.
- The subset can produce **`k(k−1)` directed events in total**. Because malicious provers can choose the hidden recipient field, it can concentrate all resulting receive receipts on one account. Its received-credit bound is therefore not merely `k−1`. Per-account receive limits may limit immediate redemption; they do not establish provenance.
- If colluders also acknowledge legitimate authorizations from outside senders, the `k` colluding prover identities can produce up to **`k(M−1)` receipts** across all named senders, including their internal events. This is an upper bound conditional on those outside senders authorizing the actions, not permission to debit strangers. All those receipts can again be designated for one cooperating account. A two-member collusion is consequently not limited to one concentrated receive credit if honest outsiders interact with it.

These are lifetime event bounds, further restricted by any enforced authorization quotas and receipt expiry. A sender's own signed-action cap still bounds its acknowledged outbound events per epoch. Pooled receive credit can defeat a stronger claim that its balance reflects its own counterpart acknowledgements, even though it cannot mint extra initial allowances or valid signatures.

Keeping the nullifier scope constant preserves the lifetime bounds across rolling balance windows. Introducing epoch or separate “introduction”/“reply” scopes multiplies the available events by those contexts and must not be treated as a harmless encoding change. Do not redeem the same receipt into several windows. Pin a common receipt key to one issuance cohort and credit both sides to that cohort's rule epoch, rather than letting delayed redemption choose a newer epoch. Otherwise an old event can become fresh balancing credit. Short expiry reduces pooling duration but narrows the anonymity set and recovery period.

This route can support **directional counters of authorized acknowledgements with explicitly poolable credit**. It cannot honestly label them nontransferable per-person delivery counters. Whether the larger collusion bound is acceptable is a policy question to measure, not a cryptographic proof of failure or success. The endorsement-only fallback remains a separate unselected candidate.

## Atomicity, retained state and privacy

The isolated [directional ledger](../experiments/directional-receipts/receipts.js) provides a joint SQLite transaction for the sender counter, consumed authorization, lifetime pair marker and cached blind response; the original independent acknowledgement and permit ledgers remain unchanged. An asynchronous signature is calculated before the transaction and returned only after successful commit; validity and allowance checks repeat under the write lock. Exact cached retries recover the original response before proof/signing work. Concurrent first attempts may perform redundant cryptography before one transaction wins, but cannot produce another counter event. Losing the response after commit does not authorize another receipt.

Recovery of an already committed response is distinct from accepting a new proof: the short qualification checkpoint might have expired while the receipt remains valid. Retain the exact response through the common receipt-recovery deadline and allow bounded retrieval of that committed result. A copied proof may win a delivery race, but must not prevent the original holder from retrieving the same result. Only the holder of the retained unblinding state can finalize its prepared receipt. Existing generic endorsements cannot be retrospectively counted as authorized sends; they contain no such signed authorization.

Redemption separately commits its anti-replay serial and authenticated account counter. Signing and later anonymous redemption cannot form a single account-pair transaction with these APIs: the issuer does not yet know the redeemer. Thus `total acknowledgedReceive ≤ total authorizedSend` for valid receipts issued only by this flow, with strict inequality possible forever after abandonment or expiry. Equal totals are not an invariant. Tracking unmatched receipts back to their sender to refund or penalize them would reintroduce the link that blindness removed.

Use distinct trusted keys for ordinary permits and receipt types, shared across a sufficiently large community/epoch cohort. An invisible payload label alone cannot prevent a malicious requester obtaining a signature for another accepted use under the same key. Never create keys per member, pair or authorization. Verifiers must enforce fixed encoding, the intended context, expiry and the recipient field. This follows the separation and message-validation requirements in [RFC 9474 §§6.2 and 7.2](https://www.rfc-editor.org/rfc/rfc9474.html#section-6.2).

Required state is bounded per-epoch authorization/retry data, receipt-spend markers through their validity window, bounded per-account epoch counters, and lifetime directed nullifiers. Prune expiring data only with a durable time/retirement floor; nullifier pruning would restore old pair opportunities. Bound pending requests, request bytes, nonce lifetime and retry work. Cheap authorization/quota checks should precede expensive proof verification; proof and quota success cannot be assumed across an asynchronous boundary. No profile, text or client-reported contact map is needed by these ledgers.

Blindness is not traffic-analysis protection. Shared transport sessions, account cookies, exact timestamps, unusual batch counts and personalized keys can join the named sender phase to the authenticated recipient phase. A complete roster of 100 identities does not supply 100 indistinguishable receipt issuances when only one happens. Anonymous, separated connections and fixed shared contexts are necessary; delayed/batched redemption can enlarge the candidate set but gives no unconditional guarantee. These deployment distinctions are part of [Privacy Pass's threat model and metadata analysis](https://www.rfc-editor.org/rfc/rfc9576.html#section-3.3). No network anonymity or batch policy is implemented here.

## Tested boundary and next increment

The tested experiment exposes **`authorizeAndAcknowledge → cached blind response`** and **`redeemAcknowledgedReceipt → authenticated counter update`**, with fixed counter names and no delivery claim. It combines the existing circuit and RSA implementation with current admission, immutable enrollment and lifetime scopes. It uses 17 authenticated synthetic identities, including 16 eligible alternatives for every sender-excluded proof. Client-owned encrypted blind-state recovery, signed release attestations, a policy controller and anonymity transport composition remain separate work.

The acceptance groups below are covered by the executable suite, with the stated scope limits:

1. No unsolicited sender/receiver counter or maturity update without that side's own authorization; reject copied grants, wrong purpose, expired authorizations and changed requests.
2. Real self-proof rejection, successful distinct proof, and exactly one sender update plus one recoverable response under concurrent replays, crashes and checkpoint changes.
3. Honest account-bound receipt redemption, wrong-account rejection, exactly-once retries and expiry/rollback rejection.
4. Demonstrate—not falsely reject—the malicious prover preparing a receipt for the original sender, and pooled receipts from a closed `k`-member set. Check both the `k−1` direct-event and `k(k−1)` concentrated-credit bounds, plus outside-sender authorizations.
5. Honest reversed action repairs directional imbalance without an ordinary-reply permit; changing roles does not count as proof of the same unordered pair or a sincere reply.
6. Abandonment leaves only the sender count; delayed redemption stays in its issuance cohort; a modified receiver can omit redemption. Tests must not assert impossible conservation or compulsory receipt recording.
7. Cross-purpose keys, request bounds, cap exhaustion and 99-recipient fan-out retain their independent limits; receipt credits never issue extra first-contact permits by themselves.
8. Inspect both wire formats and retained state for explicit pair joins. The timing diagnostic deliberately has one issuance/redemption candidate; it does not measure an anonymity network or certify anonymity from a schema test.

The 99-attempt case makes repeated authenticated redemption attempts using the 17-member fixture; it is not a 100-member capacity benchmark. Transaction fault hooks simulate application interruption around commit, not power loss. A separate fail-first regression established that a same-algorithm wrong private RSA key could debit a sender without producing a usable receipt; the tested fix binds the signing key's public parameters to the shared cohort before debit. The fixture proves actual admissions signatures, not a live independent phone/payment factor service.

The next [counter-backed attestation increment](../experiments/directional-receipts/ATTESTATION-ACCEPTANCE.md) specifies signed evidence of each committed counter, a hidden fresh release nonce and cross-language verification against cmsg's conditional release gate. It must not introduce a sender-recipient join or pretend that the two independently committed events prove the provenance of one particular blind receipt.

Exact delivery/first-send counting, compulsory truthful receive counts, prover-bound receipt ownership, global unordered first-contact uniqueness and same-pair reciprocal maturity remain open. A maturity rule based on weaker authorized directional activity would need to be named and reviewed explicitly. This study neither implements that rule nor substitutes the endorsement-only policy for it.
